## Checks selected for this project

| Priority | Check and reason | Current evidence / review boundary |
| --- | --- | --- |
| Retain | Dependency audit and PR secret scan | The existing workflow and approval rules are documented in `SECURITY-BASELINE-CI.md`. The exact, still-unfixed `braces`, `sprintf-js` and `uuid` findings are accepted only through 2026-11-09 UTC in `DEPENDENCY-AUDIT-BASELINE.json` and `DEPENDENCY-RISK-REGISTER.md`. No change to that gate is proposed here. |
| Verify | Build, runtime headers and secure configuration | `package.json` provides build/typecheck scripts and `next.config.ts` defines baseline headers. Confirm deployed responses and environment separation; a frame-only CSP is not a full script/style policy. |
| Verify | Studio identity, authorization and content governance | `sanity.config.ts` and `README.md` show editor workflows, but permissions, MFA, CORS, dataset access, token scope, authenticated publishing and photo consent require Sanity/account evidence. Review who may publish public text, images and outbound links (`sanity/schemaTypes/`, `lib/content.ts`). |
| Verify | Webhook integrity and abuse handling | `app/api/revalidate/route.ts` checks a signature before invalidating one tag. Test valid/invalid signatures and body/error behavior in a safe environment; inspect provider delivery/replay controls, secret rotation and request volume. Do not assume signature verification alone handles replay or availability. |
| Verify | Analytics, privacy and external links | The analytics component runs on both public layouts and CMS fields can supply external URLs (`app/(en)/layout.tsx`, `app/(es)/layout.tsx`, `sanity/schemaTypes/storeSettings.ts`). Determine actual telemetry, cookies, privacy notice/consent and retention with the owner. Review destination domains and published photos; schema URL validation is useful evidence, not proof about all live content. |
| Verify | Least-privilege access and recovery | `README.md` identifies Sanity and hosting setup, while `.github/workflows/security-baseline.yml` requests read-only CI permissions. Owner must inspect GitHub, hosting and Sanity accounts, MFA, deploy rights, backups and incident contacts. |

Public form, visitor-account and payment checks become applicable if those features are added. Their absence from the current source is not a permanent waiver; use the general matrix when architecture or business practice changes.

1. Which Sanity project/dataset is live, who can edit or publish, what MFA and CORS settings are enabled, and can unauthenticated clients read more than intended? Evidence: Sanity project settings and an authenticated publishing test; see `sanity.config.ts`, `sanity/lib/client.ts`, `README.md`.

3. What does the deployed site actually send through Vercel Analytics, including cookies or identifiers, and what notice, consent and retention decisions apply? Evidence: browser/network inspection plus account policy/settings; see both public `app/` layouts.
4. Are identifiable family photos/biographies or customer information published or stored, and what permissions, retention and removal process apply? Evidence: reviewed live content and owner practice; see `sanity/schemaTypes/featuredPhotos.ts`, `components/pages/StoryPage.tsx`, `lib/store.ts`.
5. Are payments, inquiries, mailing lists, or regulated data handled offline or by linked services, and in which jurisdictions? The source does not answer this; see `README.md` and `components/Sections.tsx` for the site's limited visitor flows.
6. Do production and preview have the intended headers, environment variables, access restrictions, backups and deploy permissions? Evidence: deployed response/configuration and account review; see `next.config.ts`, `.env.example`, `.github/workflows/security-baseline.yml`.

Unknown answers remain open questions, not passed controls. This profile neither certifies legal compliance nor substitutes for penetration testing or provider account review.
